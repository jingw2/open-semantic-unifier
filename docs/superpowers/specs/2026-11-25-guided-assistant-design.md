# 新手引导助手与结果可读性改造设计

日期：2026-11-25  
状态：待确认  
范围：前端交互、方法推荐、复核响应字段、在线结果查看。不改身份裁决策略，不改引擎算法。

## 1. 背景

五个问题指向同一个根因：界面把引擎、阶段、Provider、证据码和产物直接摆给用户，没有从“我要完成什么”出发。

- 左侧有 8 个一级菜单，路由、契约、实体统一、复核、发布各自独立。新用户默认落在数据源页，没有“从这里开始”。
- 实体复核卡片展示 `CANDIDATE / STRONG_IDENTIFIER_MISSING` 和原始 JSON，没有业务语言解释，也没有字段并排对比。
- L1 清洗结果、L2 簇文件、L3 契约模型只能下载；L4 结果已经在线。
- 路由工作台只写“执行建议”，没有说明用途，也没有把方法选择讲清楚。
- 后端已有按数据特征推荐 L1/L2/L4 的路由器，但没有把它翻译成“OpenRefine + W3C”或“Splink + DuckDB”。

## 2. 目标

1. 新用户进入后 30 秒内知道第一步，并且能从助手直接走到对应页面。
2. 每个页面顶部用一句话说明“这里做什么”。
3. 实体复核用人话说明“为什么需要你判断”，并给出字段对比和选择后果。
4. 主要结果可以在线查看，不必先下载文件。
5. 按用户选择的数据自动推荐 OpenRefine + W3C 契约或 Splink + DuckDB，并说明理由。
6. 保留现有 8 个菜单，不做大规模 IA 重写；用右侧助手和分组降低理解成本。

## 3. 非目标与反目标

非目标：

- 不接入自由文本 LLM 对话。v1 用确定性意图匹配和按钮引导，稳定、零额外成本。
- 不自动合并、不自动发布。助手只加载示例数据、导航和预填，所有裁决仍由人点击。
- 不删除现有页面和菜单，不改变身份裁决策略，不改变引擎算法。
- 不做真实客户数据评估。

反目标：

- 一个只会给建议、不能把用户带到正确页面的聊天框。
- 一个悄悄切换引擎、不解释理由的方法推荐。
- 一个遮挡主界面、需要额外 Key 或缺网就不可用的助手。
- 一个把原始 JSON 藏起来、只给结论不给证据的复核页。

## 4. 方案选择

考虑过三种改法：

- **A. 对话式首页 + 5 个一级入口。** 最彻底，但需要重做 IA 和现有页面的入口关系。
- **B. 首次向导 + 保留菜单。** 改动小，但 8 个菜单仍在，问题只解决一次。
- **C. 右侧助手 + 保留菜单。** 用户已选。保留现有页面，新增一个常驻助手负责引导、解释和跳转；用品类分组让 8 个菜单更好扫。

本设计按 C 展开。

## 5. 右侧助手

### 5.1 布局

- 桌面端：右侧 320px 面板，可折叠。主内容区宽度自适应，不遮住表格。
- 移动端：右下角悬浮按钮，点开为抽屉。
- 默认首次登录展开，之后记住上次状态（`localStorage`）。
- 视觉与现有 ChatGPT 风格一致：白底、细边框、黑色主按钮、无渐变。

### 5.2 状态机

助手只做四件事：问目标、看数据、给方案、带你去。

```
welcome
  你想完成什么？
  [清洗供应商名单] [跨系统匹配客户]
  [统一 GMV 口径] [生成数据契约]
  [解释当前页面]

planning
  正在读取当前项目的数据...
  没有数据时： [加载示例数据] [去上传]

plan
  建议方法：Splink + DuckDB
  理由：检测到 2 张表共 35,000 行，需要跨库匹配。
  接下来：
  ① 选数据  ② 运行  ③ 看结果
  [开始] [换一个方法]

conflict
  你选的是“清洗供应商名单”，但当前数据是 2 张共 35,000 行的大表，
  更适合 Splink + DuckDB。要按你的选择走 L1，还是改用推荐方法？
  [按我的选择走 L1] [改用 Splink + DuckDB]

navigate
  已为你打开“处理方法”，阶段已选 L2。
  运行后回到这里，我帮你看结果。
  [查看结果] [解释当前页面]
```

### 5.3 意图规则

v1 不做自由文本模型调用。输入框支持关键词匹配，匹配不到时展示四个任务按钮。

| 任务 | 关键词 | 阶段 | 方法 |
| --- | --- | --- | --- |
| 清洗供应商名单 | 清洗、名单、供应商、标准化、去重 | L1 | OpenRefine + W3C 契约 |
| 跨系统匹配客户 | 匹配、客户、跨库、关联、认亲 | L2 | Splink + DuckDB |
| 统一 GMV 口径 | 指标、GMV、口径、报表 | L4 | 指标 YAML |
| 生成数据契约 | 契约、标准、模型、LinkML、W3C | L3 | LinkML W3C 契约 |

### 5.4 助手动作

助手只调用已有 API，并且每个动作在点击前说明后果。

- 读取 `GET /api/v1/projects/{id}/datasources`，展示当前数据。用户选中某个数据源时，使用该数据源已存的 `profile` 和 `routing`；没有选中时用最新一个。前端不重算 `recommend_pipeline`，也不新增项目级聚合接口。
- 用户选的任务与数据推荐的方法冲突时，不静默覆盖。展示两种选择，由用户决定；用户的选择优先。
- 用户选“加载示例数据”时，调用 `POST /datasources/demo/{L1|L2|L4}`。按钮文案写明“将新增一份示例数据”。
- 用户点“开始”时，把 `{task, stage, datasourceIds, profile, routing}` 交给 App：
  - L1/L2/L4：设置 `activeDsIds / activeProfile / activeRouting`，打开“处理方法”，阶段预选。
  - L3：打开“契约统一”，助手说明三步：上传契约文件 → 登记契约源 → 编译并发布。
  - 复核：打开“实体统一工作台”的人工复核页，并说明当前待处理项。
- “解释当前页面”按 `nav` 返回 2 到 3 句说明，外加“你可以在这里做什么”。

### 5.5 护栏

- 不自动运行任务。只预选阶段，运行按钮仍由用户点击。
- 不自动合并、发布或修改裁决。
- 不读取或展示 Provider 凭据。
- 加载示例数据会新增数据源，按钮必须明示。重复点击允许，但提示“会再新增一份”。
- 助手失败时显示错误和“去数据源手动操作”，不阻塞页面。

## 6. 复核解释

### 6.1 后端响应

扩展 `GET /projects/{id}/unification/reviews` 的每个 item。该接口只返回 `action == "REVIEW"` 的配对；强标识冲突等 `DISTINCT` 配对不会进入这里。因此 `why` 的冲突分支用纯函数单元测试覆盖，不为了测试去扩大接口契约。

```json
{
  "left": {"record_ref": "supplier:erp:01", "attributes": {"name": "Acme Ltd", "tax_id": "TEST-TAX-001"}},
  "right": {"record_ref": "supplier:secondary:01", "attributes": {"name": "ACME, Ltd.", "tax_id": null}},
  "comparison": [
    {"field": "name", "left": "Acme Ltd", "right": "ACME, Ltd.", "status": "MATCH"},
    {"field": "tax_id", "left": "TEST-TAX-001", "right": null, "status": "MISSING"}
  ],
  "why": "名称等弱证据相似，但缺少可核对的强标识，无法自动确认是否同一实体。",
  "consequence": "确认同一实体后，两条来源记录会合并到一个实体；保持分离则保留为两个实体。"
}
```

`record_ref` 统一为 `<source_system>:<dataset>:<source_record_id>`，同时返回这三个原始字段，避免前端拆分字符串。`attributes` 只放方案 `field_map` 的规范字段子集，键用规范名，值保留原始值；状态判断用方案 normalizers 归一化后再比较。`status` 只取 `MATCH`、`DIFFERENT`、`MISSING`。`comparison` 的字段来自方案 `field_map`。`why` 由一个纯函数根据证据码确定性生成，便于直接单测：

- `STRONG_IDENTIFIER_MISSING` + `WEAK_EVIDENCE_ONLY`：名称等弱证据相似，但缺少可核对的强标识。
- `STRONG_IDENTIFIER_CONFLICT` 或 `CONFLICT_CONSTRAINT`：强标识不一致，规则要求保持分离，但名称等证据相似。
- `TRANSITIVE_CONFLICT` 或 `human_cannot_link`：此前有人或规则标记这两条记录不能合并。
- 其他：规则无法自动判定，需要你根据字段对比确认。

模型建议单独展示，不混进 `why`。模型返回 `UNKNOWN` 时显示“模型不确定”，不显示成“建议合并”。

### 6.2 前端卡片

- 标题：“这两条记录是不是同一实体？”
- 一句 `why`。
- 字段对比表：字段名、左侧值、右侧值、匹配状态。缺失值显示“未填写”，不显示空白。
- 模型建议：保留 `模型建议 · SAME` 等原文，旁边加中文解释“倾向同一实体 / 倾向不同实体 / 不确定”。置信度、分布条、模型版本、Provider 类型和 Key、耗时继续显示，`decision_models` 验收的现有断言不移除。
- 选择后果一句 `consequence`。
- 按钮保留现有文案：“确认同一实体”“保持分离”，避免破坏现有测试。
- “查看原始证据”默认折叠，点开显示现有 JSON 和证据码。`unification` 验收改为先展开再断言证据码，或断言新的 `why` 文案。

### 6.3 L2 复核队列

- 每条显示“模型认为可能是同一实体（95%）”，附模型给的理由。
- 显示左侧和右侧文本、相似度、推入原因：“L2 灰色边界样本”。
- 保留“同意合并 / 拒绝”按钮和映射规则沉淀说明。

## 7. 在线结果查看

新增 `ResultViewer` 弹窗，所有结果入口加“查看”。

| 结果 | 在线渲染 |
| --- | --- |
| `.csv` | 前 200 行表格，显示列名和总行数，底部“下载完整文件” |
| `.json` / `.yaml` | 格式化代码块；契约模型用结构化视图 |
| `.html` | iframe，复用现有 `ArtifactPreview` |
| `.sql` / `.txt` | 代码块 |
| 契约模型 | 类、属性、枚举、关系四块；可切换查看 JSON |

接入位置：

- L1：`clean_csv`、`rules_json` 加“查看”。
- L2：`clusters_csv` 加“查看”；权重图和瀑布图保持现有预览。
- L4：指标产物加“查看”，结果行已在页面展示。
- 契约统一：版本历史每行加“查看模型”，调用现有导出接口 `kind=model`。
- 发布中心：产物行加“查看”。

实现约束：

- 读取现有 `/api/v1/artifacts/{id}/content`，前端按文件名解析，不需要新后端接口。
- CSV 解析只做预览，支持引号转义；解析失败时回退为纯文本。
- 契约模型解析失败时显示原始 JSON，不白屏。
- 弹窗只读，下载仍是独立按钮。

## 8. 处理方法与方法推荐

### 8.1 页面说明

- 一级菜单“路由工作台”改名为“处理方法”。这是标签调整，不是 IA 重写。
- 页面顶部加一句：“根据数据特征选择清洗、跨库匹配或指标统一，然后运行。”
- 三阶段各一句：
  - L1 小表清洗：统一名称、空格、大小写和别名。
  - L2 跨库匹配：DuckDB 候选 + Splink 概率匹配。
  - L4 指标统一：用声明式 YAML 统一口径。
  - L3 契约统一：编译 LinkML/W3C 契约，入口在“契约统一”。
- 顶部方法卡：方法名、一句理由、可展开的现有 `reasons`。

### 8.2 后端方法字段

扩展 `recommend_pipeline` 的返回值，保持旧字段不变：

```json
{
  "method": {
    "key": "openrefine_w3c",
    "label": "OpenRefine + W3C 契约",
    "stage": "L1",
    "description": "先清洗小表，再用 LinkML/W3C 契约固化标准字段。",
    "reason": "检测到 1 张 250 行的小表，字段有空格和大小写噪声，适合先清洗再生成标准契约。"
  }
}
```

方法映射：

| key | 触发条件 | 阶段 |
| --- | --- | --- |
| `metrics_yaml` | 检测到指标 YAML，或用户指定 L4 | L4 |
| `contract_w3c` | 检测到 Schemasheets/LinkML，或用户指定 L3 | L3 |

当前 profiler 只识别 Schemasheets TSV，不识别 LinkML YAML。需要在 `profile_items` 新增 `has_linkml_contract`：YAML 同时包含 `classes:` 与 `prefixes:`、`default_range:`、`imports:` 中至少一个。否则上传 LinkML 契约会落到 L1，而不是 L3。
| `splink_duckdb` | 多表、总行数 ≥ 5 万、多维消歧键或有黑话 | L2 |
| `openrefine_w3c` | 其他小表单表 | L1 |

### 8.3 展示位置

- 数据源卡片：“建议方法：Splink + DuckDB”，按钮改名“进入处理方法”。
- 处理方法顶部方法卡。
- 实体统一工作台顶部横幅：按项目最新数据源的路由显示建议。
  - 小表：“当前数据适合先清洗并生成 W3C 契约。先去 L1 清洗，再编译契约。”按钮“去清洗” / “仍然直接匹配”。
  - 大表：“当前数据适合 Splink + DuckDB 跨库匹配。”按钮“去运行 L2” / “直接匹配”。
- 助手计划卡片。

方法推荐是建议，不是静默切换。用户仍可选择直接匹配。实体统一当前引擎不变。

## 9. 导航分组

保留 8 个菜单，只加分组标题，不改入口：

```
数据    数据源中心
处理    处理方法 / 实体统一工作台 / 契约统一
治理    人工复核队列 / 发布与对外 API
系统    模型 Provider / 团队与权限
```

## 10. API 与数据变更

- `recommend_pipeline` 新增 `method` 对象。旧客户端忽略新字段。
- `profile_items` 新增 LinkML YAML 识别，供 `contract_w3c` 使用。
- `GET /unification/reviews` 新增 `left`、`right`、`comparison`、`why`、`consequence`。旧字段保留。
- 其余复用现有接口：数据源列表、示例数据、任务提交、产物内容、契约导出。
- 无数据库迁移。

前端 Playwright：

## 13. 风险与回滚

- 助手动作会新增示例数据。按钮明示，重复点击提示会再新增；不做静默写入。
- 右侧面板占宽。默认 320px，可折叠，移动端抽屉。
- 复核响应变大。每个 item 只带两条记录的属性，规模可控。
- 契约模型结构解析失败时回退原始 JSON。
- 方法推荐只是建议。若规则判断不准，用户可直接选阶段，行为与现在一致。

## 14. 已定的实现取舍

- 助手 v1 用确定性规则，不接 LLM。后续可加 DeepSeek 生成解释，但不作为依赖。
- “路由工作台”改名为“处理方法”。如果不喜欢，改回一个字符串即可。
- 复核按钮文案保持“确认同一实体 / 保持分离”。
- 保留 8 个菜单，只加分组标题。
- 方法推荐展示理由并允许覆盖，不静默切换引擎。
- 复核卡保留 `模型建议 · SAME`、置信度、分布、Provider 元数据原文；只把证据码和原始 JSON 折叠。现有 `decision_models` 验收不动，`unification` 验收改为展开证据或断言 `why`。
- 复核接口仍只返回 `REVIEW` 配对；冲突类 `why` 只做纯函数单测，不扩大接口契约。
- 任务与数据推荐冲突时展示两种选择，用户选择优先。
- 助手使用用户选中的数据源路由，没有选中时用最新数据源的路由；不新增聚合接口。
- 新增 LinkML YAML 识别，避免契约文件误落到 L1。
- 复核响应里的 `record_ref` 为 `<source_system>:<dataset>:<source_record_id>`，`attributes` 只带 `field_map` 规范字段子集。
